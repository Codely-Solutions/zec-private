# Bounded local development

Use [dev_session.py](dev_session.py) for related compilation/unit checks, with the existing Windows resource guard and [development-policy.json](development-policy.json). Keep a source checkout, Gradle project cache and incremental outputs at stable paths until the bounded session ends. SDK/JDK/dependency caches remain managed separately. Release preparation continues to use the release workflow.

## Run related checks

Write one task-owned manifest. `source` is an absolute repository path; each operation selects a full committed source SHA. Parameters are non-secret development inputs. The root Gradle settings require the published SDK and BIP-39 dependencies, including when local Gradle arguments, user properties or environment variables supply an included-build path. For a change headed to release, include release-scoped Detekt alongside the first focused JVM tests in one Gradle invocation, before preview builds or hosted dispatch. Use the same release analysis script as hosted preflight. Example structure:

```json
{
  "source": "D:/Data/Crypto/zec-private/source",
  "seconds": 1700,
  "idle_seconds": 300,
  "operations": [{
    "source": "FULL_40_CHARACTER_COMMIT_SHA",
    "seconds": 600,
    "config": {
      "tasks": [":detektAll", ":ui-lib:testZcashmainnetFossDebugUnitTest"],
      "tests": ["co.electriccoin.zcash.ui.common.model.RecipientAddressPolicyTest"],
      "init_scripts": [".private/release-analysis.gradle", ".private/tor-ui-abi.gradle", ".private/robolectric-ci.gradle"]
    }
  }]
}
```

Run with the managed Python interpreter (or `python3` where configured):

```text
python3 -B .private/dev_session.py TASK/inputs.json --evidence TASK/checks
```

The evidence directory must be new. Debug build tasks, unit tests and `:detektAll` analysis are accepted; production release assembly/signing is outside this helper. `tests` filters apply to each explicitly requested JVM test task, directly after its task name; analysis and assembly tasks receive none. For production Detekt scope, include `.private/release-analysis.gradle`. Optional `jdk`, `sdk` and `gradle_home` paths select existing reviewed installations. `--policy` selects a reviewed guard override; the project default caps memory at 8 GiB and transient storage at 18 GiB. Admission still checks host headroom.

For checks added while editing, set an absolute task-owned `inbox`. Atomically rename a complete operation JSON to `0001.json`, `0002.json`, etc., counting initial operations too. Pin a new commit for each source change. `finish.json` ends an idle session; the idle and total deadlines also end it. One controller owns each session.

Each operation has immutable source/configuration/tool bindings, bounded process ownership, task outcomes and copied JUnit/timing evidence. Rejected pins still get their own failed receipt. JUnit collection requires the requested task's current execution, cache restoration or up-to-date outcome. Failed executions contribute only changed reports; unchanged XML from an earlier operation remains with its original receipt. Up-to-date reports retain their original producer's operation, source and binding. Cache-restored reports identify the current restoration rather than claiming fresh execution. Timing files require a current change. Evidence-collection failure rejects the operation while preserving its primary error. A failing command ends the session; correct its boundary before starting another. Completed session receipts are verified/archived locally before their shared-ledger entry is retired. Run `test_dev_session` for this provenance boundary.

Include `.private/robolectric-ci.gradle` for MockK JVM checks. It loads the Byte Buddy agent selected by the resolved test runtime at JVM startup, with a declared classpath input and committed SHA-256 verification. The agent version follows its parent dependency constraint; the agent itself is not in the dependency lockfiles. Startup instrumentation avoids the external self-attachment process that can fail inside bounded Windows jobs. It adds no dependency or machine setting and also runs in the maintained hosted release suite. See [MockK's startup-agent guidance](https://github.com/mockk/mockk/blob/master/doc/md/jep451-dynamic-agent-loading.md). Preserve unrelated JDK/compiler diagnostics.

The root build verifies the API 28 and 34 Robolectric sandbox JARs through Gradle and stages them once for the offline resolver in every Robolectric JVM test. A warm local Maven cache is outside this path. When updating Robolectric or a test's configured Android API, verify the required artifact from Maven Central and update the pinned coordinates and hashes together.

For an explicit dependency-checksum bootstrap, set `config.write_verification_metadata` to `["sha256"]`. The controller passes Gradle's generation flag before startup, copies the resulting `gradle/verification-metadata.xml` into that operation's evidence directory with its SHA-256, and restores the checkout's original metadata bytes or original absence before the next operation. Metadata input and export are capped at 4 MiB. The export requires changed bytes or a different file identity on the same metadata path. An unchanged file, a timestamp-only update and a byte-identical in-place rewrite cannot establish generation from this check. If execution and export both fail, the runner failure stays primary and the receipt records the export failure separately. Original bytes are restored in either case. Review the exported XML and provenance before committing it. Normal validation omits this option and uses strict verification from the committed metadata. Generated checksums record the resolved bytes; independently establish publisher provenance for critical artifacts. For verification failures, use `-Dorg.gradle.dependency.verification.console=verbose` or retain Gradle's HTML report before teardown. See [Gradle dependency verification](https://docs.gradle.org/current/userguide/securing_dependencies.html).

For a cold CI metadata proposal, manually dispatch the existing `toolchain-review.yml` with `metadata_proposal=true`. Its default remains the strict configuration/resource-tool smoke. The opt-in mode runs Gradle's `dependencies` reports across retained projects and a representative library resource compilation (including host-specific AAPT2) with `--write-verification-metadata sha256 --refresh-dependencies`; it performs no app assembly, test, signing or acceptance task. The three-day artifact contains proposed XML (at most 4 MiB), source/run/hash/exit identities, a resolution-failure line count, up to 64 KiB of failure lines and the final 64 KiB of the log. Check the exit code and resolution diagnostics, review the XML diff and publisher provenance, then apply reviewed additions and rerun strict validation. Gradle may omit detached configurations created only during task execution; this proposal does not establish complete build coverage or acceptance. See [Gradle's generation and review limits](https://docs.gradle.org/current/userguide/dependency_verification.html).

All checkout/build/guest scratch is removed when its guard ends. There is no long-lived daemon or cross-session workspace store. On pause, finish the session and retain only named offline artifacts/evidence; the next session recreates missing state.

On Windows, the session gives child JVMs a deliberately absent owned `jdk.net.unixdomain.tmpdir`. The pinned JDK's selector falls back to loopback TCP when its preferred Unix-domain listener cannot bind. This avoids transient AF_UNIX reparse files in the guarded root while preserving the guard's reparse-point rejection. The child options join the operation binding; existing options and machine configuration remain intact.
