# Phase 1 validation record

Runtime implementation and prepublication acceptance passed; revision 5 is not published yet.

Approved scope: remove Flexa, coinholder voting implementation and redundant promotional/feedback surfaces. Preserve core wallet operations, gift cards, hardware/view-only accounts, migration/repair and CrossPay. Inspection classified the Ironwood announcement as a funds-migration guide; it remains with the operational migration warnings. What's New points to fork releases.

The first measured dependency comparison used current-release source `dd8629826` and candidate `74f54938a`, CI run `42053515212`. Its digest-verified artifact is recorded in `phase1-runtime-baseline.json`. Baseline: 351 components; initial candidate: 333. That comparison also revealed implicit Compose 1.10.6→1.10.4 and Room 2.7.2→2.7.0 downgrades when removing Flexa. Explicit constraints now preserve the already shipped effective versions; the comparison gate rejects changes to retained versions. Google lists newer stable Compose 1.12.1 and Room 2.8.5 as of 2026-11-05; a general library upgrade is outside this removal phase, and compatibility of those newer versions is not claimed. Sources: https://developer.android.com/jetpack/androidx/releases/compose-ui and https://developer.android.com/jetpack/androidx/releases/room .

The first full unit run compiled the app and ran 1,390 tests: 3 constructor failures from eager main-dispatcher access in the Flexa-independent error mapper. The replacement scope is now lazy, preserving construction without a platform dispatcher. Final suite results remain pending.

Controller simulations exposed two maintenance issues and blocked integration as intended: patch generation must exclude the separately hashed/sanitized upstream NEAR provider; imported checks must not generate bytecode in the integration candidate. Patch generation has been corrected, and the controller invokes Python with `-B` plus ignored generated bytecode. Final controller results remain pending.

Unfunded production API contracts passed through a dedicated Tor process in CI run `42054124382`. The contract client now requires SOCKS5 with remote DNS and has no direct fallback. Final source-bound release evidence will be collected again by the production pipeline.

Local guard tests initially exceeded its per-receipt bound when listing every scanned source. The maintained source manifest is now verified before and after broad scans while the small control implementation set is registered directly. Fixture cleanup is deferred to guard finalization to avoid a concurrent scan/delete race. Local control receipt `929fc9d5b8b547e0aaadabb59bef9a2b` passed with cleanup; it predates subsequent edits and is not final acceptance evidence.

The corrected controller simulation `42057791966` passed. Two additional fail-closed Tor tests must still pass in the final production build.

The final upgrade profile models an installed wallet with a Tor-warmed catalog and allows a bounded longer startup; this is not evidence that cold Tor startup latency has been fixed.
