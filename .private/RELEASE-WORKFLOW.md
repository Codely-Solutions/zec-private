# Prepare and validate a release candidate

## Hosted custom releases

Keep held work on its branch. Run targeted development checks there. When ready, prepare one reviewed commit directly on the current protected `main`, advance the private revision and Android version code, and add `.private/custom-candidate.json` with `kind: custom` and `controller` set to the full parent SHA. Remove any inherited `.private/candidate.json`, stage the reviewed changes and refresh the canonical fork patch and source state with `python -B .private/refresh_source.py`. Push the prepared commit to its candidate branch. Keep controller and signing changes in their separate trusted review path.

Add the new tag's user-facing changes to [release-notes.json](release-notes.json) in the candidate. Use the [custom workflow](../.github/workflows/custom-release.yml) on `main`. Use `check` for candidate, dispatcher and changelog admission alone. Use `preflight` to diagnose the shared release checks on GitHub or verify signing wiring through the actual reusable caller. It stops after recording APK job admission and cannot assemble APKs, run wallet acceptance, reserve funds or publish. For a normal release, dispatch `publish` directly so the pipeline runs preflight once.

```sh
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=check -f source_sha=FULL_REVIEWED_SHA
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=preflight -f source_sha=FULL_REVIEWED_SHA
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=publish -f source_sha=FULL_REVIEWED_SHA
```

Use `publish` after the user authorizes releasing the reviewed change. Bind the dispatch to the exact prepared SHA and use the allowlisted GitHub account. An authorized dispatch runs the shared hosted build and wallet/quote acceptance, then signs and publishes if all gates pass. The custom path runs outside the monthly cadence and leaves the routine slot available.

If preparation or recovery changes the SHA, compare the replacement with the approved change and inspect the intervening controller diff. Carry approval forward for the same reviewed release after routine build fixes, version preparation or rebasing onto a compatible controller. Record the comparison, bind the new dispatch to its exact SHA and run the required checks. Get fresh approval if the release scope changes materially, signing or acceptance safeguards change, or the user expressly limits approval to a particular SHA.

For a pre-publication failure, diagnose the affected job and recover the original run where its artifacts are still live and its controller is current. Preserve the claim reservation if funding occurred or is uncertain. For a public APK awaiting verification or recording, use [publication reconciliation](MAINTENANCE.md#signing-and-publication) with the original run ID. Fixture preservation uses the original hosted test pair.

If acceptance needs a controller repair, use `custom-release.yml` with `operation=recover`, the original `source_sha` and `recover_run=ORIGINAL_RUN_ID`. Recovery requires successful APK producers, a skipped publisher and live artifacts. Review the controller diff before deploying it. For a quote failure, retain the passing wallet receipt and rerun the quotes on the original emulator APK. If the entire wallet workflow was skipped before reservation or execution, run it once with the original testnet APKs and reuse the original quote receipt when it passed. The signer rechecks the original artifact digests, both acceptance run identities and the protected reservation. The existing release authorization applies.

If that recovery passes quotes and the signer fails before creating an attestation, diagnose and fix signing, then add `quote_run=PASSING_QUOTE_RUN_ID` to reuse the passing quote receipt. The controller checks that the quote execution inputs match, and signing checks all three run identities. Reconcile an existing public release through its original attestation.

If skipped-wallet recovery reserved funding but its baseline network startup failed before wallet creation or any faucet request, diagnose that boundary with the unfunded transport probe. With positive pre-claim evidence, dispatch recovery with `preclaim_run=FAILED_WALLET_RECOVERY_RUN_ID`. The original reservation remains protected. The new run checks the prior wallet log and reservation, completes quote acceptance first, then may create one linked reservation. A failed or uncertain claim is ineligible.

Pass the named environment secret references when invoking the reusable release workflow. Their values come from `production-signing` and `maintenance-integration` only in the jobs that select those environments. Keep repository-level copies absent.

## Shared release preflight

Hosted admission checks the exact candidate and changelog before one preflight job runs offline checks, the [live swap catalog check](INDEPENDENT-PRICES.md), fast regressions, acceptance selection, and strict Linux Gradle configuration plus release Detekt. The catalog check uses the controller's checker and the candidate's mappings. A mismatch or failed fetch stops the candidate before Gradle or APK assembly. The unsigned production, emulator and testnet APK jobs share that gate and can start together. The wallet and quote acceptance jobs can overlap when their respective APKs are ready. Artifact promotion and quote-only recovery reuse the original build evidence. Reconciliation of an already published release starts from its original attestation.

Preflight fingerprints the trusted signing workflows, key check and publisher, along with the live `production-signing` policy. GitHub must restrict that environment to the `main` branch. A changed fingerprint checks that credentials are absent in the ordinary job and proves access to the pinned key in the protected job with a disposable certificate request. Record the fingerprint and passing GitHub run ID in [signing-smoke.json](signing-smoke.json) after verifying both steps. Ordinary candidates then skip the key check. After rotating credentials, reset that record to `null` and use `preflight` through the custom caller. Credential values are outside the fingerprint.

## Hosted maintenance releases

The [upstream discovery workflow](../.github/workflows/sync-upstream.yml) polls every three hours. The routine release window opens on the first of each month at 09:00 UTC, starting December 1, 2026. It selects the latest stable upstream release and highest compatible verified Gradle patch available by that cutoff. Upstream releases and open Dependabot proposals are the queue. A missed poll can catch up within the window, and later arrivals roll into the next batch. The first verified routine publication in a window closes it. An empty window produces no APKs. A failed batch keeps its inputs queued. Keep any existing claim reservation and use the original run for recovery.

To expedite an applicable security fix, push the exact reviewed `security-maintenance.patch` and its [review record](security-maintenance.json) to protected `main`. That push starts discovery immediately. Record `advisory`, `advisory_repository`, `advisory_updated_at`, `affected_release`, `affected_source`, `scope` (`wallet` or `release-pipeline`), `exposure`, `fix`, and `patch_sha256`. Cite the affected configuration or call path and the supported upstream fix in the review. Generate the patch with `git diff --binary` against current main, omitting the release version bump, and hash the committed patch bytes. The controller checks the publisher's current GitHub advisory, the affected public APK and the exact patch. It stages the fix alone and rejects unshipped product changes on main. Keep signing and controller changes in their separate trusted review path. Reset the record to `null` after retirement. An alert, label or PR description grants no expedited admission.

The cadence and candidate checks run before [release validation](../.github/workflows/build-release.yml), and signing rechecks eligibility. Admission also checks the private fixture and claim reservation. GitHub enforces Actions storage limits. Secretless jobs build each APK once. Separate hosted guests run the funded testnet lifecycle and unfunded production quote checks. Recovery of an already published release runs independently of the calendar.

The [hosted core workflow](../.github/workflows/hosted-core.yml) verifies the pinned Tor Project Linux Expert Bundle before creating a protected `testnet-claims/release-<versionCode>` ref. The wallet job verifies the staged runtime by artifact ID and checksums. The ref binds the controller, candidate and run. A duplicate ref, ambiguous create response or subsequent attempt cannot authorize another claim. Keep the reservation if funding is uncertain. After a successful wallet job, recover a failed signing job using the original run and live artifacts. An already public release uses [publication reconciliation](MAINTENANCE.md#signing-and-publication).

The main-only signing job fetches the unsigned APK and the two receipts by artifact ID and rechecks their digests, source, test APK producers, acceptance fingerprints and claim reservation. Independent public verification rechecks the same unsigned artifact. Fixture preservation publishes the original testnet pair to the private registry and updates the hosted baseline after a separate read-back. Its timer can recover a missing fixture from the verified release record and original Actions artifact while that artifact is live.

A manual dispatch of `hosted-core.yml` runs a testnet-only rehearsal from the selected fixture. It uses a separate reservation and cannot supply a release receipt. Use `upgrade_probe=restore` or `upgrade_probe=transport` to isolate that boundary after an installed upgrade without reserving or claiming funds. A later `rehearsal_number` requires diagnosed prior failures and a newer trusted controller. Prior reservations stay protected.

The Tor outage test requires parsed updater metadata before the interruption, a blocked updater request during it, and a real response after Tor recovers. A confirmed GitHub quota response proves reachability only. Independent publication verification still checks actual release discovery.

## Guarded local acceptance

Use these maintained tools from the selected checkout. They prepare or validate acceptance; they do not dispatch a build, sign or publish. Obtain publication authorization separately. Read [resource lifetimes](MAINTENANCE.md#reuse-and-cleanup) before starting workers.

1. Commit the reviewed candidate and select its verified paired upgrade baseline. Run `acceptance_status.py` with child environment `VALIDATION_ONLY=true` to see pending profiles and changed-input reasons. A pending result is not acceptance.
2. Build required variants once through the existing producer workflows when authorized. Check existing runs and artifacts for reuse and review job warnings. Preserve the immutable production APK for later promotion.
3. Run `prepare_release.py --help`. Supply the exact source SHA, production producer run, resource owner and a fresh `--out` directory beneath the project's `work/`. Select `--profile core` and/or `--profile quotes` for pending execution; core needs its paired producer run. Version and baseline identities come from the committed source. Preparation verifies live metadata and writes bound jobs/manifests; it starts no guest.
4. Inspect `preparation.json`. Parallel execution needs matching stable-peer identities, passing targeted checks and at least 16 GiB available RAM; missing evidence selects sequential work. `--planning-evidence` supplies that explicit evidence. The execution guard rechecks resources and artifact bindings. A plan is not an acceptance receipt.
5. Run `admit_release.py --prepared PREPARED_DIRECTORY --owner OWNER --profile core` or `--profile quotes`. Pass both only for an eligible parallel plan. `--image` accepts the existing verified managed image. Keep dependent wallet stages sequential; a peer failure cancels the batch, so resolve uncertain diagnostics independently first.
6. Run `assemble_release.py --help`. Select the exact candidate/run/task identities and each fresh `--core-batch`/`--quote-batch` or validated `--reuse-core`/`--reuse-quote` receipt. Reused receipts retain their original bytes and executed-build identity. Assembly writes a fresh staging directory and rejects mismatches; it does not overwrite historical evidence or install acceptance automatically.
7. Review staged results and their scope before the authorized promotion procedure. Keep build and attesting-controller identities distinct. Preserve signing isolation and promote the validated production artifact without rebuilding it.

The native lifecycle already checks RPC before wallet creation. It now checks faucet status before creating wallet state, retaining one owned Tor process through the subsequent claim. Unavailable prerequisites stop that boundary; status success cannot guarantee payout. The exclusive claim ledger and single-submit rules remain authoritative. Use [funding diagnostics](MAINTENANCE.md#testnet-funding-and-failed-boundaries) after a failure rather than restarting a funded sequence.

Acceptance remains conservative: swap composition can invoke local wallet funding. Product swap changes select both existing profiles until a narrower dependency boundary is proven. Host-only changes can reuse compiled artifacts where their fingerprints permit; they still invalidate affected execution evidence. Documentation and status reports explain reuse without relabeling an older APK as newly executed.

Keep task inputs and outputs under one owned task directory. Admission closes owned workers; reconcile files, worktrees, sessions and remote outputs before handoff. Retire prepared APKs after their final consumer, preserving required fixtures, compact receipts and original evidence. Historical release scripts are provenance, not current entry points.
