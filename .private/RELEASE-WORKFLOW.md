# Prepare and validate a release candidate

## Hosted custom releases

Keep held work on its branch. Run targeted development checks there. When ready, prepare one reviewed commit directly on the current protected `main`, advance the private revision and Android version code, and add `.private/custom-candidate.json` with `kind: custom` and `controller` set to the full parent SHA. Remove any inherited `.private/candidate.json`, stage the reviewed changes and refresh the canonical fork patch and source state with `python -B .private/refresh_source.py`. Push the prepared commit to its candidate branch. Keep controller and signing changes in their separate trusted review path.

Add the new tag's user-facing changes to [release-notes.json](release-notes.json) in the candidate. Use the [custom workflow](../.github/workflows/custom-release.yml) on `main`. Use `check` for candidate, dispatcher and changelog admission alone. Use `preflight` to diagnose the shared release checks on GitHub or verify signing wiring through the actual reusable caller. It stops after recording APK job admission and cannot assemble APKs, run wallet acceptance, reserve funds or publish. For a normal release, dispatch `publish` directly so the pipeline runs preflight once.

```sh
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=check -f source_sha=FULL_REVIEWED_SHA
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=preflight -f source_sha=FULL_REVIEWED_SHA
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=publish -f source_sha=FULL_REVIEWED_SHA
```

Use `publish` after the user authorizes releasing the reviewed change. Publish and preflight require a prepared custom candidate. Use recovery selectors only with `recover` and supply the original APK-producing run. Recovery can select an eligible discovery run. Bind the dispatch to the exact prepared SHA and use the allowlisted GitHub account. An authorized dispatch runs the shared hosted build and wallet/quote acceptance, then signs and publishes if all gates pass. The custom path runs outside the monthly cadence and leaves the routine slot available.

If preparation or recovery changes the SHA, compare the replacement with the approved change and inspect the intervening controller diff. Carry approval forward for the same reviewed release after routine build fixes, version preparation or rebasing onto a compatible controller. Record the comparison, bind the new dispatch to its exact SHA and run the required checks. Get fresh approval if the release scope changes materially, signing or acceptance safeguards change, or the user expressly limits approval to a particular SHA.

## Release recovery

Identify the last verified stage and keep the original run, candidate SHA and artifact IDs. Use the original artifacts while their digests and provenance still match.

Use the [Kotlin resolution procedure](DEVELOPMENT.md#kotlin-plugin-resolution) for missing build-plugin metadata. The emulator and bridge can recover a verified miss within their existing job. If recovery fails, diagnose the exact repository, coordinate and restored cache before retrying. Retain passing producers and receipts; retire only proven stale entries when necessary.

| Last verified stage | Next action and required evidence |
| --- | --- |
| Before a faucet POST | Fix the failed readiness boundary and use the unfunded probe when needed. If preparation failed before reservation and wallet execution, resume those stages using the original APKs. Reuse the parallel quote receipt when it passed. If a protected reservation exists, pass the original or failed wallet recovery run as `preclaim_run` after reviewing the newer controller. Admission requires positive no-POST evidence at startup, readiness or the funding cutoff and permits one linked reservation. The original reservation stays protected. A passing original quote receipt can precede the linked reservation. |
| Claim sent or uncertain | Preserve the reservation and reconcile the original claim. If the disposable wallet is gone and acceptance cannot resume, document the cause and prepare a reviewed replacement after correction. From current main, run `python3 -B .private/release_inputs.py --replacement-of ABANDONED_VERSION_CODE` for unused version coordinates. This read-only command does not change the candidate or advance the maintenance timer. |
| Wallet or installed upgrade receipt passed | Reuse it and run any missing quotes against the original emulator APK, including when the sibling quote job was cancelled. An unchanged controller can retry once when the original job identifies a Tor HTTP transport or independent market timeout. A trusted job creates `testnet-claims/quote-recovery-ORIGINAL_RUN_ID` atomically. Leave it protected so repeated dispatches cannot reuse the retry. For other interruptions, continue on a reviewed descendant controller. |
| Funded provenance qualifies and the unfunded installed upgrade failed | Keep the protected original claim, reuse the passing quote receipt and compatible prepared pair, and rerun the installed upgrade without a faucet call. |
| Wallet or installed upgrade and quotes passed | After signing failure or cancellation, reuse the passing receipts and original APKs for signing. Select any receipt produced by a later recovery with `core_run` or `quote_run`. A retained publication attestation requires reconciliation, including when the same publisher run is rerun before it creates a draft. The signer rechecks wallet and quote execution inputs for both original and separately selected receipts. |
| Draft or orphan tag after signing | Use [publication reconciliation](MAINTENANCE.md#signing-and-publication) with the original run, attempt and attestation ID. |
| APK public | Use [publication reconciliation](MAINTENANCE.md#signing-and-publication) with the original attestation and run. Preserve the original public assets and accepted testnet pair. |

```sh
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=recover -f source_sha=FULL_REVIEWED_SHA -f recover_run=ORIGINAL_RUN_ID
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=recover -f source_sha=FULL_REVIEWED_SHA -f recover_run=ORIGINAL_RUN_ID -f preclaim_run=FAILED_WALLET_RUN_ID
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=recover -f source_sha=FULL_REVIEWED_SHA -f recover_run=ORIGINAL_RUN_ID -f core_run=PASSING_WALLET_RUN_ID -f quote_run=PASSING_QUOTE_RUN_ID
```

Recovery requires successful APK producers and live bound artifacts. A failed rerun can leave valid first-attempt artifacts available. Admission matches each retained archive to the successful job whose execution window contains its upload, and checks every attempt for a successful publisher. Use the same authorized dispatch for an unpublished automatic upstream, Gradle wrapper or reviewed security run. Pass its exact prepared candidate SHA and original `sync-upstream.yml` run. Admission rechecks the original maintenance provenance and the current eligibility of that maintenance revision.

Keep `recover_run` set to the original APK-producing run. Use `core_run` for a later recovery that passed wallet acceptance or the installed upgrade. Use `quote_run` for a later recovery that passed quotes. Select either passing receipt even if a sibling job stopped. Use both selectors when separate recovery runs supplied the receipts. Full receipt reuse skips acceptance and creates no funding or quote retry reservation.

Admission and signing check the trusted producer attempts, completed acceptance jobs, original APK bindings, fixture, and applicable protected reservations. A later publication controller must preserve the selected acceptance inputs. If the bounded same-controller quote retry passed, use its run as `quote_run` or rerun its failed signing jobs on the unchanged controller. Both paths verify the existing retry reservation against the passing job in attempt 1. Before signing, the controller checks retained trusted attestations for the same tag or Android version code, including separate recovery runs that reused all prior receipts. If an attestation exists, reconcile that exact publisher even if it stopped before creating the draft.

A wallet-only runner repair can retain the passing quote. Shared workflow changes must keep the selected stage's jobs and shared artifact-producing inputs byte for byte. Edits to publication or reporting jobs can reuse receipts. If an admitted repair changes quote execution inputs, collect a fresh unfunded quote receipt on the original APKs and preserve any compatible wallet receipt. Changes to shared artifact staging or wallet validation require current wallet evidence. Preserve the original artifacts and reservation while diagnosing a mismatch.

Quote recovery reuses a live bridge artifact from the same trusted controller when available. A changed controller or an expired bridge prepares a new bridge before quotes. Any previously accepted quote receipt selected for recovery keeps its original bridge provenance. Hosted quote failures report sanitized application stages. The unfunded scenario can retry a Tor HTTP request that ends without a response when the current attempt records the observed runtime failure. Retries stay within the existing per-cycle budget. The receipt requires at least three successful reviews and dismissals and one independent comparison. When the first two comparisons fail, the scenario waits for the provider backoff to clear and allows one extra unfunded quote if needed.

For a linked pre-claim recovery, the controller completes quote acceptance before creating the linked reservation. Reusing that wallet receipt requires compatible quote-before-claim wiring. Admission keeps the original no-POST proof after a rerun if later attempts skipped wallet execution and either skipped reservation or copied the original successful reservation job. If the prior recovery passed quotes and failed to prepare wallet instrumentation before reservation, pass its run as `quote_run`. Admission verifies the prior job states, receipt bytes, direct route and original APK bindings before allowing the wallet job. Keep that quote selector if the subsequent wallet job passes and a later signing recovery is needed.

Pass the named environment secret references when invoking the reusable release workflow. Their values come from `production-signing` and `maintenance-integration` only in the jobs that select those environments. Keep repository-level copies absent.

### Discovery delay and recovery monitoring

The existing external six-hour heartbeat monitors `sync-upstream.yml`; keep the three-hour GitHub schedule and monthly release cutoff. Compare the latest scheduled start with current queued/in-progress runs and their job progress. A late scheduled start with completed controllers is a scheduler delay. A queued controller or a running controller with stalled job progress needs queue/job diagnosis. A healthy active run needs no duplicate dispatch.

The heartbeat is read-only. When discovery is over eight hours late and no run is queued or active, an authorized maintainer can dispatch `sync-upstream.yml` on `main` once and follow that exact run. Recheck the queue immediately before dispatch. Existing concurrency, candidate selection and closed-window checks preserve idempotence. Protected claim reservations and release gates remain authoritative. The heartbeat reports an actionable blockage and treats routine delays, inconclusive data and successful catch-up as quiet outcomes.

For an unrecorded public release, the watcher searches retained release attestations across paginated repository artifacts, then passes the exact publisher run, attempt and artifact ID into reconciliation. Indexed names let it skip unrelated release tags before reading proof bytes. The inventory request has a time limit. If that read fails, retry the watcher or supply the exact verified publisher. The resolver requires a unique live attestation matching the trusted attempt, source tag, APK and checksum.

For a recorded public release, the watcher checks open publication blockers and queues reconciliation when a retained publisher attestation matches the blocker and the full recorded evidence. If the original workflow lost the acknowledgement and left no blocker, dispatch reconciliation with its original publisher run, attempt and attestation ID.

A failed proof read leaves automatic selection unresolved, even when another proof matches. Retry discovery after the read recovers or supply the verified original publisher run, attempt and attestation ID. A draft-recovery dispatch checks signing readiness in a credential-free job before it enters the protected environment. If signing is paused, the run reports the blocker against that exact publisher.

When only integration is rerun, the publisher job's retained outputs identify the original signing attempt, archive and digest. Integration verifies that attempt against the attestation before recording the release.

The main discovery caller reports watcher and preparation failures independently, including when the watcher prevents preparation from starting. The shared release workflow reports a failed protected quote-retry reservation even when quotes and publication skip. Its diagnosis names the reservation; retain the protected one-use ref and investigate the failing job before recovery. Notification tests evaluate each failed prerequisite separately, with successful/skipped controls and closed quote/publication gates. These reports do not authorize another reservation or relax attestation requirements.

The read-only watcher follows its caller's lifetime and has no shared concurrency group. Scheduled, security-push and manual discovery on `main` share one replaceable pending slot. Other refs stop at admission before the discovery queue. Discovery and shared release callers report failure or independent cancellation of each declared prerequisite. Whole-run cancellation stays quiet.

The open blocker issue retains a separate diagnosis for each operation, candidate and applicable validation profile. An exact publisher attestation has its own section, including when a later build or admission fails for the same candidate. Its writers share a serialized queue and preserve the newest run and attempt for each diagnosis. Delivery acknowledgement reloads the issue and updates the matching revision, preserving operator notes visible at that read. A manual body edit between the read and the subsequent GitHub update can still be overwritten. Delivered repeats update quietly. A changed diagnosis or undelivered message remains eligible.

Verified reconciliation retires the original publisher attestation and any matching unresolved run-only selector. A failed later build or admission stays open until its own scope recovers. A directly verified release can also resolve an earlier build blocker for its candidate. For the matching revision, discovery recovery requires both the watcher and preparation to succeed. Validation recovery requires the unsigned build and any requested emulator build to succeed. Emulator-inclusive validation also resolves unsigned-only and existing unprofiled validation blockers for the same revision. Diagnostic recovery records the result quietly. Review blockers from superseded revisions and unrecognized issue sections explicitly. Verified recovery removes resolved sections and records any pending automation-owned close in the same body update. If the close is interrupted, a later verified recovery or suppressed old failure can finish it. Operator text and unrecognized or unrelated blocker sections are preserved. `test_maintenance_watch` and `test_notify` exercise these consumers with GitHub and push I/O mocked.

Every verified success advances its scope's run and attempt order, even when the matching failure has yet to arrive. Keep the markers in the open blocker issue or the latest closed history. On a clean repository, the first success creates and closes a verified recovery history issue. Retain the latest 16 discovery identities separately from 64 other operation/candidate/profile/attestation identities, deduplicating each before eviction. Older or equal workflow ordering cannot reopen a scope with a retained marker. A newer failure remains eligible. Legacy manual closures and evicted markers supply no ordering evidence. Exact publisher recovery also retires that publisher's unresolved run-only selector. Known distinct archives and publishers remain independent.

Publication-attestation lookup requires successful signing and a retained archive created during the original trusted upload step. An upload can persist the archive before its acknowledgement fails or is cancelled. Recover that exact archive only when its size, digest and upload interval match. Reject failed signing, missing archives, copied-attempt timestamps and archives outside the original upload window. New artifact names index the attested Android version code and release tag. The original names remain readable. Pre-draft recovery checks the original attested changelog before opening the signing key. Preserve independent APK, certificate, payload and tag verification.

New attestations carry the signing publisher run and attempt. After independent public verification, integration can acknowledge an existing protected-main record whose complete evidence matches the original attestation and whose history contains the attested controller and candidate. A conflicting record stops recovery. A matching record uses the normal success notice without acquiring a writer token. If the normal Git push returns an error or times out, read protected main and report success only when its tip equals the exact prepared commit. Otherwise use the usual failure and reconciliation path.

## Shared release preflight

Production and recovery share a workflow queue. Validation and simulated upgrades have separate workflow queues that preserve pending production work. A full simulation from main requires signing readiness before preparation. Review refs can exercise unsigned diagnostics. The rehearsal verifies the synthetic source, original quote-rendering failure, live contract and runtime graph. Its protected workflow produces a diagnostic signing receipt. After a rehearsal failure, diagnose the failed step and dispatch a fresh rehearsal. The run removes its disposable source and APK inputs. Normal publication still requires candidate-specific wallet and quote acceptance. Every job that opens the permanent signing key, including the standalone environment smoke check, joins the same serialized signing job queue. That queue uses `queue: max` and preserves running jobs. Admission rechecks the current main controller. Promotion and recovery revalidate exact retained producer identities and artifact expiry. The original expiry still applies while work is queued. [GitHub concurrency contract](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)


Hosted admission checks the exact candidate and changelog before one preflight job runs offline checks, the [live swap catalog check](INDEPENDENT-PRICES.md), fast regressions, acceptance selection, and strict Linux Gradle configuration plus release Detekt. The catalog check uses the controller's checker and the candidate's mappings. A mismatch or failed fetch stops candidate Gradle validation and APK assembly. In a release or recovery that needs fresh quotes, the secretless [quote bridge job](../.github/workflows/quote-bridge.yml) runs alongside preflight after admission. Fresh hosted production, emulator and testnet APK jobs start together after both gates pass. The bridge refreshes dependencies once when Gradle reports missing Kotlin API or BOM POMs and Maven Central serves the exact coordinates. Quote acceptance downloads by artifact ID and verifies the producer run, controller, archive digest and APK hash. The receipt records the original bridge identity before emulator-only signing preparation. Preflight-only runs retain their check-only behavior. The wallet and quote acceptance jobs can overlap when their respective APKs are ready. Artifact promotion and quote-only recovery reuse the original build evidence. Reconciliation of an already published release starts from its original attestation.

To verify the bridge handoff alone, dispatch `hosted-acceptance-probe.yml -f test_quote_bridge=true` on the reviewed ref. The probe builds and verifies the bridge artifact with read-only permissions and skips the app APK, emulator and all release jobs.

Publication and explicit custom preflight fingerprint the trusted signing workflows, including the upgrade acceptance simulation, the key check and publisher, along with the live `production-signing` policy. Validation-only builds on `main` perform that check while `PRODUCTION_SIGNING_READY` is `true`. During signing setup or pause, they skip the environment lookup and key-access smoke and can still build unsigned APKs. GitHub must restrict the environment to the `main` branch. A changed fingerprint checks that credentials are absent in the ordinary job and proves access to the pinned key in the protected job with a disposable certificate request. Record the fingerprint and passing GitHub run ID in [signing-smoke.json](signing-smoke.json) after verifying both steps. Ordinary candidates then skip the key check. After rotating credentials, reset that record to `null` and use `preflight` through the custom caller. Credential values are outside the fingerprint.

## Hosted maintenance releases

The [upstream discovery workflow](../.github/workflows/sync-upstream.yml) polls every three hours. The routine release window opens on the first of each month at 09:00 UTC, starting December 1, 2026. It selects the latest stable upstream release and highest compatible verified Gradle patch available by that cutoff. Upstream releases and open Dependabot proposals are the queue. A missed poll can catch up within the window, and later arrivals roll into the next batch. The first verified routine publication in a window closes it. An empty window produces no APKs. A failed batch keeps its inputs queued. Keep any existing claim reservation and use the original run for recovery.

The watcher reads open pull requests in creation order, up to ten pages of 100. When it needs another page, it requires two complete listings with the same ordered pull request numbers. It rereads each listed Dependabot proposal to check the current target, draft state, head and file diff. Duplicate entries, a changed inventory, a full final page or a proposal that changes during verification leave selection unresolved for discovery to retry. The listing is an observation of current work. Later additions are picked up on subsequent runs.

Before returning a standalone or combined wrapper candidate, staging checks the open non-draft proposal, exact base and head, and current protected main again. The check applies to fresh staging and reuse of an existing matching tree. Recovery of an earlier admitted release keeps its original artifact and evidence bindings.

The [controller](maintenance_cadence.py) reads `ZCASH_SDK_VERSION` from the exact selected upstream commit at the monthly window. It checks ten Maven Central coordinates for the corresponding stable version. Require both the POM and AAR for `zcash-android-sdk`, `zcash-android-backend`, `zcash-android-sdk-incubator`, `lightwallet-client` and `zcash-android-sdk-slipstream`. A confirmed 404 keeps upstream queued and lets a due Gradle patch proceed independently. A complete SDK set admits the same upstream commit to the compatibility checks. An unclear SDK declaration, registry error or moved tag requires diagnosis before upstream preparation proceeds.

Discovery checks the exact `refs/heads/main` before entering the production discovery queue. The admitted reusable workflow holds that queue through preparation and nested release work. When recovering a publication, verify the original run, attempt, job and attestation. The verifier recognizes both the original `build / …` job names and `discover / build / …` for this discovery workflow.

Supply a positive run ID for public reconciliation. Supply both the positive attempt number and attestation artifact ID to select an exact publisher. Draft recovery requires the exact pair. The admission job marks malformed or conflicting inputs and fails with a dispatch diagnostic. Operational failures before selector admission send a maintainer notification with the workflow link when push delivery is configured. Durable publisher blockers require an admitted selector. An exact verified recovery clears its matching blocker and the matching run-only blocker.

To expedite an applicable security fix, push the exact reviewed `security-maintenance.patch` and its [review record](security-maintenance.json) to protected `main`. That push starts discovery immediately. Record `advisory`, `advisory_repository`, `advisory_updated_at`, `affected_release`, `affected_source`, `scope` (`wallet` or `release-pipeline`), `exposure`, `fix`, and `patch_sha256`. Cite the affected configuration or call path and the supported upstream fix in the review. Generate the patch with `git diff --binary` against current main, omitting the release version bump, and hash the committed patch bytes. The controller checks the publisher's current GitHub advisory, the affected public APK and the exact patch. It stages the fix alone and rejects unshipped product changes on main. Keep signing and controller changes in their separate trusted review path. Reset the record to `null` after retirement. An alert, label or PR description grants no expedited admission.

The cadence and candidate checks run before [release validation](../.github/workflows/build-release.yml), and signing rechecks eligibility. Admission also checks the private fixture and claim reservation. GitHub enforces Actions storage limits. Secretless jobs build each APK once. Separate hosted guests run the funded testnet lifecycle and unfunded production quote checks. Recovery of an already published release runs independently of the calendar.

## Guarded local acceptance

Use these maintained tools from the selected checkout. They prepare or validate acceptance; they do not dispatch a build, sign or publish. Obtain publication authorization separately. Read [resource lifetimes](MAINTENANCE.md#reuse-and-cleanup) before starting workers.

1. Commit the reviewed candidate and select its verified paired upgrade baseline. Run `acceptance_status.py` with child environment `VALIDATION_ONLY=true` to see pending profiles and changed-input reasons. A pending result is not acceptance.
2. Build required variants once through the existing producer workflows when authorized. Check existing runs and artifacts for reuse and review job warnings. Preserve the immutable production APK for later promotion.
3. Run `prepare_release.py --help`. Supply the exact source SHA, production producer run, resource owner and a fresh `--out` directory beneath the project's `work/`. Select `--profile core` and/or `--profile quotes` for pending execution. Core needs its paired producer run. The committed local fixture must name both original APK hashes and agree with the current verified hosted pair. Fresh funded acceptance downloads the authenticated producer archives and checks the original APK digests before starting the guest. Prepared diagnostic APKs stay outside release acceptance. Assembly reads the same descriptor and verifies the executed baseline app hash before staging the receipt. Preparation and promotion require the selected run to have passed and verify live artifact metadata. The prepared manifests bind each archive to the original successful job and attempt whose execution window contains the upload. A successful rerun with a copied job preserves that binding for the retained archive. Preparation writes the bound jobs and manifests without starting a guest.
   For local quotes, supply `--bridge-run` from the passing `ui-bridge.yml` workflow on that exact main commit. The producer checksums its dependencies. The receipt binds its archive, execution and recipe inputs. Reuse requires those inputs to match. Older receipts without the binding remain historical and require a fresh quote check for direct promotion. Hosted quote acceptance keeps its separate producer binding.
4. Inspect `preparation.json`. Parallel execution needs matching stable-peer identities, passing targeted checks and at least 16 GiB available RAM; missing evidence selects sequential work. `--planning-evidence` supplies that explicit evidence. The execution guard rechecks resources and artifact bindings. A plan is not an acceptance receipt.
5. Run `admit_release.py --prepared PREPARED_DIRECTORY --owner OWNER --profile core` or `--profile quotes`. Pass both only for an eligible parallel plan. `--image` accepts the existing verified managed image. Keep dependent wallet stages sequential; a peer failure cancels the batch, so resolve uncertain diagnostics independently first.
6. Run `assemble_release.py --help`. Select the exact candidate/run/task identities and the guarded receipt for each profile. Direct wallet acceptance must bind the current candidate source and Android version. Use `--reuse-core` only to stage that candidate's existing receipt. Reused receipts retain their original bytes and executed-build identity. Assembly writes a fresh staging directory with both receipt digests and the exact unsigned archive and producer. Review and commit the three staging files before promoting an existing run. Promotion checks that run against the assembly, and signing rechecks the archive, original producer and receipt bytes.
7. Review staged results and their scope before the authorized promotion procedure. Direct publication requires the guarded local pair to match the latest public tag, source, version and both original baseline APK hashes of the hosted pair. Hosted direct acceptance can prepare a source-bound instrumentation APK. Its receipt carries both the retained fixture identity and the prepared instrumentation binding through exposure and draft reconciliation. The controller checks this before the build and again at signing admission. Routine watch, fixture preparation and adoption, hosted admission, quote recovery, signing and public exposure verify the integrated tag object, APK, checksum and the version line the Android updater reads. Validate the public record independently of the next fixture so fixture recovery can proceed after a newly verified publication. Before resuming an unpublished draft, confirm that its attested baseline still matches the latest public release. Recheck at public exposure. If the baseline has changed, reconcile the intervening release before selecting new acceptance. Already-public reconciliation can verify the original publication with its original evidence. Historical pairs remain available for diagnostics. Local fixture preservation resumes by verifying any existing draft assets independently, uploading missing assets and rebuilding the index only after both assets are verified. Keep build and attesting-controller identities distinct. Promote the validated production artifact through isolated signing.

The native lifecycle checks RPC and faucet status before creating wallet state, retaining one owned Tor process through the subsequent claim. Unavailable prerequisites stop that boundary. Status success cannot guarantee payout. Local admission checks the retained Android version ledger and current verified upgrade pair before starting the funded worker. The worker rechecks the prepared pair against the current public release after proof work and before creating the attempt ledger. A changed pair stops at the upgrade baseline stage with no claim. The exclusive ledger stays outside the disposable guest and the single-submit rule remains authoritative. Use [funding diagnostics](MAINTENANCE.md#testnet-funding-and-failed-boundaries) after a failure with a recorded attempt.

Acceptance remains conservative: swap composition can invoke local wallet funding. Product swap changes select both existing profiles until a narrower dependency boundary is proven. Host-only changes can reuse compiled artifacts where their fingerprints permit; they still invalidate affected execution evidence. Documentation and status reports explain reuse without relabeling an older APK as newly executed.

Keep task inputs and outputs under one owned task directory. Admission closes owned workers; reconcile files, worktrees, sessions and remote outputs before handoff. Retire prepared APKs after their final consumer, preserving required fixtures, compact receipts and original evidence. Historical release scripts are provenance, not current entry points.
