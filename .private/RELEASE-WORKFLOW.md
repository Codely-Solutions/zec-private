# Prepare and validate a release candidate

## Hosted custom releases

Keep held work on its branch. Run targeted development checks there. When ready, prepare one reviewed commit directly on the current protected `main`, advance the private revision and Android version code, and add `.private/custom-candidate.json` with `kind: custom` and `controller` set to the full parent SHA. Remove any inherited `.private/candidate.json`, stage the reviewed changes and refresh the canonical fork patch and source state with `python -B .private/refresh_source.py`. Push the prepared commit to its candidate branch. Keep controller and signing changes in their separate trusted review path.

Compare the candidate with the latest verified public tag and check every material shipped outcome against its [release notes](MAINTENANCE.md#release-descriptions). Use the [custom workflow](../.github/workflows/custom-release.yml) on `main`. Use `check` for candidate, dispatcher and changelog admission alone. Use `preflight` to diagnose the shared release checks on GitHub or verify signing wiring through the actual reusable caller. It stops after recording APK job admission and cannot assemble APKs, run wallet acceptance, reserve funds or publish. For a normal release, dispatch `publish` directly so the pipeline runs preflight once.

```sh
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=check -f source_sha=FULL_REVIEWED_SHA
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=preflight -f source_sha=FULL_REVIEWED_SHA
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=publish -f source_sha=FULL_REVIEWED_SHA
```

Use `publish` after the user authorizes releasing the reviewed change. Bind the dispatch to the exact prepared SHA and use the allowlisted GitHub account. An authorized dispatch runs the shared hosted build and wallet/quote acceptance, then signs and publishes if all gates pass. The custom path runs outside the monthly cadence and leaves the routine slot available.

If preparation or recovery changes the SHA, compare the replacement with the approved change and inspect the intervening controller diff. Carry approval forward for the same reviewed release after routine build fixes, version preparation or rebasing onto a compatible controller. Record the comparison, bind the new dispatch to its exact SHA and run the required checks. Get fresh approval if the release scope changes materially, signing or acceptance safeguards change, or the user expressly limits approval to a particular SHA.

## Release recovery

Identify the last verified stage and keep the original run, candidate SHA and artifact IDs. Use the original artifacts while their digests and provenance still match.

Use the [Kotlin resolution procedure](DEVELOPMENT.md#kotlin-plugin-resolution) for missing build-plugin metadata. The emulator and bridge can recover a verified miss within their existing job. If recovery fails, diagnose the exact repository, coordinate and restored cache before retrying. Retain passing producers and receipts; retire only proven stale entries when necessary.

| Last verified stage | Next action and required evidence |
| --- | --- |
| Before a faucet POST | Fix the failed readiness boundary and use the unfunded probe when needed. If the wallet job never ran, recover the original artifacts and reuse its quote receipt if available. If a protected reservation exists, pass the original or failed wallet recovery run as `preclaim_run` after reviewing the newer controller. Admission requires positive no-POST evidence at startup or pre-claim readiness and permits one linked reservation. The original reservation stays protected. |
| Claim sent or uncertain | Preserve the reservation and reconcile the original claim. If the disposable wallet is gone and acceptance cannot resume, document the cause and prepare a reviewed replacement after correction. From current main, run `python3 -B .private/release_inputs.py --replacement-of ABANDONED_VERSION_CODE` for unused version coordinates. This read-only command does not change the candidate or advance the maintenance timer. |
| Wallet receipt passed | Recover the quote job against the original emulator APK and wallet receipt. An unchanged controller can retry once when the original job identifies a Tor HTTP transport or independent market timeout. A trusted job creates `testnet-claims/quote-recovery-ORIGINAL_RUN_ID` atomically. Leave it protected so repeated dispatches cannot reuse the retry. For a test/controller defect, review the narrow controller repair first. |
| APK public | Use [publication reconciliation](MAINTENANCE.md#signing-and-publication) with the original attestation and run. Preserve the original public assets and accepted testnet pair. |

```sh
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=recover -f source_sha=FULL_REVIEWED_SHA -f recover_run=ORIGINAL_RUN_ID
gh workflow run custom-release.yml --repo Codely-Solutions/zec-private --ref main -f operation=recover -f source_sha=FULL_REVIEWED_SHA -f recover_run=ORIGINAL_RUN_ID -f preclaim_run=FAILED_WALLET_RUN_ID
```

Recovery requires successful APK producers, a skipped publisher and live artifacts. The signer rechecks candidate and artifact digests, both acceptance run identities, the funding reservation and, for an unchanged controller, the exact retry reservation. The existing release authorization applies.

If that recovery passes quotes and the signer fails before creating an attestation, diagnose and fix signing, then add `quote_run=PASSING_QUOTE_RUN_ID` to reuse the passing quote receipt. The controller checks that the quote execution inputs match, and signing checks all three run identities. Reconcile an existing public release through its original attestation.

If a targeted build rerun produced the last required APK, start wallet acceptance in a fresh `recover` run on a reviewed descendant controller. GitHub's rerun attempts cannot reserve or claim testnet funds. Use the original publication run ID and exact candidate SHA. The controller checks every attempt for wallet and reservation activity, verifies that signing and publication stopped, and binds each retained APK and passing quote receipt to its original upload. If this recovery stops before the faucet POST and leaves a reservation, use its run as `preclaim_run` on a reviewed newer controller. The linked recovery keeps the original passing quote receipt. Preserve spent or uncertain reservations and all original APKs.

A targeted rerun can finish successfully with the wallet and publisher skipped. If the original run qualified for funded reuse, recovery requires the same verified funded receipt and upgrade fixture on both controllers, and no reservation for the candidate. Pass the original run ID without quote or pre-claim overrides. Recovery keeps the passing quote receipt and any live, verified direct preparation artifact. It runs fresh unfunded installed-upgrade acceptance before publication.

Quote recovery reuses a live bridge artifact from the same trusted controller when available. A changed controller or an expired bridge prepares a new bridge before quotes. Any previously accepted quote receipt selected for recovery keeps its original bridge provenance. Hosted quote failures report sanitized application stages. The unfunded scenario can retry a Tor HTTP request that ends without a response when the current attempt records the observed runtime failure. Retries stay within the existing per-cycle budget. The receipt requires at least three successful reviews and dismissals and one independent comparison. When the first two comparisons fail, the scenario waits for the provider backoff to clear and allows one extra unfunded quote if needed.

For a linked pre-claim recovery, the controller completes quote acceptance before creating the linked reservation. If the prior recovery passed quotes and failed to prepare wallet instrumentation before reservation, pass its run as `quote_run`. Admission verifies the prior job states, receipt bytes, direct route and original APK bindings before allowing the wallet job.

Pass the named environment secret references when invoking the reusable release workflow. Their values come from `production-signing` and `maintenance-integration` only in the jobs that select those environments. Keep repository-level copies absent.

### Discovery delay and recovery monitoring

The existing external six-hour heartbeat monitors `sync-upstream.yml`; keep the three-hour GitHub schedule and monthly release cutoff. Compare the latest scheduled start with current queued/in-progress runs and their job progress. A late scheduled start with completed controllers is a scheduler delay. A queued controller or a running controller with stalled job progress needs queue/job diagnosis. A healthy active run needs no duplicate dispatch.

The heartbeat is read-only. When discovery is over eight hours late and no run is queued or active, an authorized maintainer can dispatch `sync-upstream.yml` on `main` once and follow that exact run. Recheck the queue immediately before dispatch. Existing concurrency, candidate selection and closed-window checks preserve idempotence. Protected claim reservations and release gates remain authoritative. The heartbeat reports an actionable blockage and treats routine delays, inconclusive data and successful catch-up as quiet outcomes.

For an unrecorded public release, the watcher searches retained release attestations across paginated repository artifacts, then invokes the existing exact-run resolver. Newer workflow runs do not displace the original publisher. The search is bounded to ten pages of 100 artifacts and stops with an explicit manual exact-run recovery instruction if that budget is exhausted. Expired attestations cannot authorize recovery. The resolver still binds the trusted publisher, live original attestation and unchanged public assets.

## Shared release preflight

Hosted admission checks the exact candidate and changelog before one preflight job runs offline checks, the [live swap catalog check](INDEPENDENT-PRICES.md), fast regressions, acceptance selection, and strict Linux Gradle configuration plus release Detekt. The catalog check uses the controller's checker and the candidate's mappings. A mismatch or failed fetch stops candidate Gradle validation and APK assembly. In a release or recovery that needs fresh quotes, the secretless [quote bridge job](../.github/workflows/quote-bridge.yml) runs alongside preflight after admission. Fresh hosted production, emulator and testnet APK jobs start together after both gates pass. The bridge refreshes dependencies once when Gradle reports missing Kotlin API or BOM POMs and Maven Central serves the exact coordinates. Quote acceptance downloads by artifact ID and verifies the producer run, controller, archive digest and APK hash. The receipt records the original bridge identity before emulator-only signing preparation. Preflight-only runs retain their check-only behavior. The wallet and quote acceptance jobs can overlap when their respective APKs are ready. Artifact promotion and quote-only recovery reuse the original build evidence. Reconciliation of an already published release starts from its original attestation.

To verify the bridge handoff alone, dispatch `hosted-acceptance-probe.yml -f test_quote_bridge=true` on the reviewed ref. The probe builds and verifies the bridge artifact with read-only permissions and skips the app APK, emulator and all release jobs.

Preflight fingerprints the trusted signing workflows, key check and publisher, along with the live `production-signing` policy. GitHub must restrict that environment to the `main` branch. A changed fingerprint checks that credentials are absent in the ordinary job and proves access to the pinned key in the protected job with a disposable certificate request. Record the fingerprint and passing GitHub run ID in [signing-smoke.json](signing-smoke.json) after verifying both steps. Ordinary candidates then skip the key check. After rotating credentials, reset that record to `null` and use `preflight` through the custom caller. Credential values are outside the fingerprint.

## Hosted maintenance releases

The [upstream discovery workflow](../.github/workflows/sync-upstream.yml) polls every three hours. The routine release window opens on the first of each month at 09:00 UTC, starting December 1, 2026. It selects the latest stable upstream release and highest compatible verified Gradle patch available by that cutoff. Upstream releases and open Dependabot proposals are the queue. A missed poll can catch up within the window, and later arrivals roll into the next batch. The first verified routine publication in a window closes it. An empty window produces no APKs. A failed batch keeps its inputs queued. Keep any existing claim reservation and use the original run for recovery.

The [controller](maintenance_cadence.py) reads `ZCASH_SDK_VERSION` from the exact selected upstream commit at the monthly window. It checks the corresponding stable version on Maven Central for both the POM and AAR of `zcash-android-sdk`, `zcash-android-backend`, `zcash-android-sdk-incubator` and `lightwallet-client`. A confirmed 404 keeps upstream queued and lets a due Gradle patch proceed independently. A complete SDK set admits the same upstream commit to the existing compatibility checks. An unclear SDK declaration, registry error or moved tag requires diagnosis before upstream preparation proceeds.

To expedite an applicable security fix, push the exact reviewed `security-maintenance.patch` and its [review record](security-maintenance.json) to protected `main`. That push starts discovery immediately. Record `advisory`, `advisory_repository`, `advisory_updated_at`, `affected_release`, `affected_source`, `scope` (`wallet` or `release-pipeline`), `exposure`, `fix`, and `patch_sha256`. Cite the affected configuration or call path and the supported upstream fix in the review. Generate the patch with `git diff --binary` against current main, omitting the release version bump, and hash the committed patch bytes. The controller checks the publisher's current GitHub advisory, the affected public APK and the exact patch. It stages the fix alone and rejects unshipped product changes on main. Keep signing and controller changes in their separate trusted review path. Reset the record to `null` after retirement. An alert, label or PR description grants no expedited admission.

The cadence and candidate checks run before [release validation](../.github/workflows/build-release.yml), and signing rechecks eligibility. Admission also checks the private fixture and claim reservation. GitHub enforces Actions storage limits. Secretless jobs build each APK once. Separate hosted guests run the funded testnet lifecycle and unfunded production quote checks. Recovery of an already published release runs independently of the calendar.

## Reuse funded wallet acceptance

The [funded selector](funded_reuse.py) compares the candidate and chosen upgrade fixture with the latest original funded release. Wallet code and retained runtime, build, identity and configuration inputs must match. The selector accepts explicitly reviewed presentation-only blob transitions and keeps unknown changes in the funded comparison. It checks the pinned signing identity, protected claim reservation, original receipt and public APK digest. Keep the exact original receipt and its source, artifact and fixture bindings when reusing it.

The [authorship migration record](published-history-migration.json) binds Release 27's unchanged source tree and public APK to its rewritten tag. Verification still checks the original unsigned producer and signed payload. Historic fixtures and receipts keep their original Git identities. Content comparisons resolve only the listed, tree-verified replacements. The migrated one-claim refs retain their original names, reservation messages and rules. New releases and reservations use exact commit IDs.

A matching candidate runs a fresh installed update with the currently selected testnet pair, direct app networking and an empty isolated wallet. It verifies the current APK and installed wallet data across the update, then restores the test seed without funding. Keep the fresh quote receipt bound to that candidate. The upgrade job has read-only permissions and skips faucet reservation. Signing rechecks both receipts and promotes the validated production APK. Independent public verification checks the signed package, version, checksum, certificate and updater path. Preserve the candidate pair from the installed-update receipt for the next release. Keep its original funded provenance separate.

Independent verification first checks the public latest-release API used by the updater. If the runner hits GitHub’s public API quota, verify the unauthenticated latest-release redirect and match it to read-only API metadata. Public APK and checksum downloads, signature checks and payload comparison still run. The verifier reports which discovery route passed.

When an older run already built the candidate or spent its claim, apply this policy through the existing exact `operation=recover` dispatch. Reuse live APKs, passing quote evidence and the compiled direct pair from the completed original run. Leave the original claim protected. A mismatch in wallet, upgrade or signing inputs selects the funded lifecycle. A malformed protected receipt or mismatched artifact blocks promotion.

The [hosted core workflow](../.github/workflows/hosted-core.yml) verifies the pinned Tor Project Linux Expert Bundle before creating a protected `testnet-claims/release-<versionCode>` ref. The CI bootstrap downloads the exact bundle and detached signature from Tor Project’s permanent release archive so later upstream releases do not remove the pinned download. The wallet job verifies the staged runtime by artifact ID and checksums. The ref binds the controller, candidate and run. A duplicate ref, ambiguous create response or subsequent attempt cannot authorize another claim. Keep the reservation if funding is uncertain. After a successful wallet job, recover a failed signing job using the original run and live artifacts. An already public release uses [publication reconciliation](MAINTENANCE.md#signing-and-publication).

Hosted release wallet and quote acceptance runs with the wallet's Tor setting off. The full funded upgrade, review, send, restart and restore still run. Before the faucet POST, the baseline pair restores an empty test seed with Tor off and the sender reports real synchronization. Standalone Tor still protects the isolated faucet request and the separate live API contract check using public test addresses. Signed publication verification checks the live updater separately. The release JVM suite continues to enforce fail-closed app routing and the exceptions for normal DNS and public bulk data.

The wallet observes the exact faucet transaction in the existing guest. A stalled scan can reset the synchronizer once while continuing to wait for that transaction. A failed observation reports the isolated testnet transaction ID for reconciliation. The one-claim rule still applies. The test invokes the app's Review accessibility action and verifies the resulting proposal. It can repeat Review once if the unchanged form remains visible with no proposal, submission or rejection. It invokes final payment approval once and tracks that exact transaction through restart and restore. Proposal failures record safe UI and SDK categories.

When changed runtime inputs could affect Tor, the unfunded native probe runs against the exact candidate testnet APK before the faucet POST. The signer requires that result for those inputs. The independent monitor checks the installed fixture daily at 06:17 UTC and records its result in the Actions summary. Use `hosted-acceptance-probe.yml -f test_preclaim=true` to run the same readiness check on demand. Add `-f compare_testnet_tls=true` to compare the same public testnet gRPC endpoint through standalone Tor, or use `-f test_transport=true` for the unfunded interruption check. These modes have read-only access and use the exact selected release pair.

The main-only signing job fetches the unsigned APK and the two receipts by artifact ID and rechecks their digests, source, test APK producers, acceptance fingerprints and claim reservation. Independent public verification rechecks the same unsigned artifact. Older pairs can use freshly compiled direct-capable instrumentation bound to the original app APK and source. Fixture preservation publishes the accepted testnet app and its matching instrumentation to the private registry and updates the hosted baseline after a separate read-back. Its timer can recover a missing fixture from the verified release record and original Actions artifact while that artifact is live.

A manual dispatch of `hosted-core.yml` runs a testnet-only rehearsal from the selected fixture. It uses a separate reservation and cannot supply a release receipt. Use `upgrade_probe=restore` or `upgrade_probe=transport` to isolate that boundary after an installed upgrade without reserving or claiming funds. A later `rehearsal_number` requires diagnosed prior failures and a newer trusted controller. Prior reservations stay protected.

The Tor outage test requires parsed updater metadata before the interruption, a blocked updater request during it, and a real response after Tor recovers. The test retries the initial read once on an I/O error through the same app Tor path. Phase markers identify the last successful readiness step. A confirmed GitHub quota response proves reachability only. Independent publication verification still checks actual release discovery.

## Guarded local acceptance

Use these maintained tools from the selected checkout. They prepare or validate acceptance; they do not dispatch a build, sign or publish. Obtain publication authorization separately. Read [resource lifetimes](MAINTENANCE.md#reuse-and-cleanup) before starting workers.

1. Commit the reviewed candidate and select its verified paired upgrade baseline. Run `acceptance_status.py` with child environment `VALIDATION_ONLY=true` to see pending profiles and changed-input reasons. A pending result is not acceptance.
2. Build required variants once through the existing producer workflows when authorized. Check existing runs and artifacts for reuse and review job warnings. Preserve the immutable production APK for later promotion.
3. Run `prepare_release.py --help`. Supply the exact source SHA, production producer run, resource owner and a fresh `--out` directory beneath the project's `work/`. Select `--profile core` and/or `--profile quotes` for pending execution; core needs its paired producer run. Version and baseline identities come from the committed source. Preparation verifies live metadata and writes bound jobs/manifests; it starts no guest.
4. Inspect `preparation.json`. Parallel execution needs matching stable-peer identities, passing targeted checks and at least 16 GiB available RAM; missing evidence selects sequential work. `--planning-evidence` supplies that explicit evidence. The execution guard rechecks resources and artifact bindings. A plan is not an acceptance receipt.
5. Run `admit_release.py --prepared PREPARED_DIRECTORY --owner OWNER --profile core` or `--profile quotes`. Pass both only for an eligible parallel plan. `--image` accepts the existing verified managed image. Keep dependent wallet stages sequential; a peer failure cancels the batch, so resolve uncertain diagnostics independently first.
6. Run `assemble_release.py --help`. Select the exact candidate/run/task identities and each fresh `--core-batch`/`--quote-batch` or validated `--reuse-core`/`--reuse-quote` receipt. Reused receipts retain their original bytes and executed-build identity. Assembly writes a fresh staging directory and rejects mismatches; it does not overwrite historical evidence or install acceptance automatically.
7. Review staged results and their scope before the authorized promotion procedure. Keep build and attesting-controller identities distinct. Preserve signing isolation and promote the validated production artifact without rebuilding it.

The native lifecycle already checks RPC before wallet creation. It now checks faucet status before creating wallet state, retaining one owned Tor process through the subsequent claim. Unavailable prerequisites stop that boundary; status success cannot guarantee payout. The exclusive claim ledger and single-submit rules remain authoritative. Use [funding diagnostics](MAINTENANCE.md#testnet-funding-and-failed-boundaries) after a failure rather than restarting a funded sequence.

Acceptance remains conservative: swap composition can invoke local wallet funding. Product swap changes select both existing profiles until a narrower dependency boundary is proven. Host-only changes can reuse compiled artifacts where their fingerprints permit; they still invalidate affected execution evidence. Documentation and status reports explain reuse without relabeling an older APK as newly executed.

Keep task inputs and outputs under one owned task directory. Admission closes owned workers; reconcile files, worktrees, sessions and remote outputs before handoff. Retire prepared APKs after their final consumer, preserving required fixtures, compact receipts and original evidence. Historical release scripts are provenance, not current entry points.
