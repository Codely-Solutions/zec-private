# Core acceptance coverage

Current publication evidence is selected by [the release procedure](RELEASE-WORKFLOW.md). Hosted releases use the verified pair in [hosted-fixture.json](hosted-fixture.json); [upgrade-baseline.json](upgrade-baseline.json) retains the local acceptance baseline. Each `release-evidence/vX.Y.Z-private.N.json` binds its original checks and artifacts. Historical receipts retain their executed baseline and scope. This document describes the covered boundaries; passing acceptance does not establish every screen, provider response or settlement case.

Testnet instrumentation uses real installed app dependencies and production wallet/proposal repositories. The opt-in app-access probe exercises Android device-PIN approval; it does not establish physical biometric behavior or production NEAR settlement. Production quotes remain unfunded. Testnet/debug and production ARM64 release builds differ in network configuration, signing and optimization; report those boundaries with results.

For direct SDK probes, give storage to the executing target UID and use unique database aliases, directories and preference prefixes. Label context setup and cleanup separately from SDK stages.

Acceptance selection and fingerprints share the same profile input function. Product swap changes remain covered by both broad gates: quote composition can choose local funding and shared amount behavior, so screen-path exclusions alone are insufficient. Status reports name the changed inputs for invalidated evidence. The current core fingerprint conservatively includes retained runtime/build inputs and the core harness/policy. Version labels, documentation, images, theme-only code and unrelated test-source changes do not invalidate wallet transaction acceptance. Unknown retained code/configuration does. A receipt also binds the exact older build revision and executed APK; evidence reuse never relabels an older binary as the current binary.

Hosted release admission applies the [funded reuse procedure](RELEASE-WORKFLOW.md#reuse-funded-wallet-acceptance). A matching candidate carries forward the original funded transaction receipt and adds a fresh, unfunded installed-update receipt for the selected baseline and current APK. The new pair becomes the upgrade baseline after publication. The installed-update receipt establishes storage and restore behavior on the current build. Transaction and settlement claims retain the original funded source and APK identities.

The executed-build fingerprint and host-harness binding are separate. A host driver correction can rerun acceptance against the same immutable APK when its relevant compiled inputs still match. Changing instrumented Kotlin or its Gradle setup requires new instrumentation. An explicit core-runtime fingerprint excludes only the one private instrumentation Kotlin file; full acceptance and compiled-build fingerprints still bind it. This permits a new test APK against unchanged production inputs. Changing its Gradle setup still requires a new production candidate. The host guard independently binds the actual launcher, preparation helpers, SDK tools and private manifest used for that execution.

Candidate builds may finish while real acceptance is pending. Signing can attach a later controller-owned receipt only when the intervening Git diff contains the explicit receipt/document allowlist. Runtime source, build files, workflow and controller changes require a new candidate. The sole additional late-source exception is the explicitly bound private instrumentation Kotlin file, validated against matching runtime inputs and its new compiled APK. Both promotion and signing check that boundary; the signed release records the original build revision and the attesting controller revision. This permits overlap of required acceptance and release preparation without another APK build or access to signing secrets from build work.

Funding follows [the maintained faucet procedure](MAINTENANCE.md#testnet-funding-and-failed-boundaries): verify testnet identity, wallet health and spendability through pinned owned Tor before one claim. Preserve and reconcile a failed or uncertain claim before another attempt. Faucet readiness does not establish a payout. Executed funding amounts, work durations and transport observations belong to the immutable release record selected by [published status](STATUS.md).

Relevant ordinary test changes select deterministic regression checks and upstream review. They do not automatically require a fresh live transaction when the app and core acceptance producer remain unchanged. The private live producer itself is included in its receipt fingerprint.

The checked-in workflows define current schedules: upstream discovery runs every three hours and the isolated Linux Android host probe runs daily. These probes establish their named prerequisites and unfunded behavior; each release still needs its selected acceptance. Measure build/setup, Tor bootstrap, faucet wait, scanning, confirmation and active assertion time separately. Public-chain or provider failures remain unverified acceptance, with a classified cause; they are not converted into passing app results.

Automated ARM hardware testing is outside scope. The user will exercise production on their phone. Keep that evidence separate from emulator execution and binary inspection.

The transaction producer launches the real app Activity and requires its foreground state. A headless process correctly stops Slipstream synchronization, so process initialization alone does not establish a usable wallet. Before any faucet claim, the current sender synchronizer must either catch up or demonstrate advancing scanned height against a non-null network tip within 120 seconds. Fresh-wallet catch-up then overlaps the faucet confirmation wait; the funding stage still requires the actual received transaction and normal spendability. Diagnostics retain status and heights, never seeds.

The emulator firewall allows current Running Tor relays plus the SDK 6.0.0 embedded Tor 0.43.0 bootstrap IP/port pairs. The latter are extracted from the published crate and checked against the SDK lockfile checksum; changing SDK version requires reviewing this inventory. The public testnet bulk endpoint on TCP443 and its normal DNS are permitted. Direct provider destinations and other app egress remain blocked. Sensitive metadata is checked separately while Tor is interrupted and direct bulk TLS remains reachable. Historical failed diagnostic runs are not passing acceptance.

Transport scope follows the user clarification of 2026-11-06. The earlier blanket DNS/egress denial blocked upstream’s intentional direct bulk path. The native SDK replacement and baseline Tor bridge were removed; production keeps the published SDK. `clearnet_fallback=false` describes sensitive requests, while `direct_bulk_downloads=true` explicitly records the permitted path. Historical failed runs and discarded native builds are diagnostic evidence only.

Use the core receipt's `network_enforcement` and `direct_bulk_downloads` fields for transport claims. The auxiliary emulator setup receipt retains a legacy `route: native SDK Tor only` selector label; it identifies the enabled SDK privacy transport and does not establish full-tunnel routing. Public bulk downloads and normal DNS remain permitted, as the actual firewall and core receipt record.

The runtime negative probe covers SDK endpoint validation (`getServerInfo` and `getLatestBlockHeight`) while the direct bulk TLS endpoint stays reachable. The firewall cannot classify encrypted RPC methods sharing that endpoint. Other sensitive transaction routing is inspected in the pinned SDK source and exercised with Tor enabled; no outage is injected during an ambiguous broadcast. Receipts state these separate evidence scopes.

Sender accounting follows the SDK's `abs(accountBalanceDelta)`: an external send debits the payment plus its fee. The sender assertion checks that total debit, fee and final balance. A clean recipient restoration independently checks the payment amount, memo and mined transaction identity. Submission is invoked once; a resubmittable SDK gRPC result can remain under observation. Acceptance requires mined history and records the app's confirmation state separately; a mined recipient transaction may still be Pending under its confirmation policy. No manual rebroadcast is used.

Representative unit cases cover 0/6/8/18 decimal atomic units across all three quote modes, and exact recipient/refund pass-through for BTC, EVM, Solana and XRP address families in both directions. These are request-boundary tests, not execution of every asset or validation of every chain's address grammar. The current quote DTO has no separate destination memo/tag field; the live Zcash transfer covers the supported wallet memo path.

The bounded sandbox review is recorded in `core-provider-review.json`. Tidepool advertises a 1Click-compatible testnet service, but its detailed documentation described the TAZ bridge as disabled, and the published OpenAPI did not establish a shielded Zcash route. Tor compatibility and actual BTC/TAZ settlement were not verified. Adoption is deferred; this prerequisite does not claim testnet cross-chain settlement or a live provider refund.

Production Detekt retains its rules and existing baseline. Its release-only init excludes the procedural private instrumentation source, which is outside the shipped source sets and separately compiled by the core producer. That harness is checked through exact source/APK bindings, review and real execution. This does not exempt production Kotlin or the ordinary unit tests from analysis.

## Retained dependency-security work

The unchanged SDK 6.0.0 pinned source lock has known Rustls, h2, constant-time arithmetic, Tokio and compression advisory matches. Tor/transparent-input source features reach some affected dependencies; actual published AAR feature union and exploitable call paths remain unresolved. Review supported SDK fixes and native build provenance before claiming these risks resolved; registry presence alone establishes neither an exploit nor immunity. Relevant examples: [Rustls protocol defect](https://rustsec.org/advisories/RUSTSEC-2026-0285.html), [constant-time arithmetic](https://rustsec.org/advisories/RUSTSEC-2026-0387.html). No newer supported Maven SDK was found during this review.

Fixed upstream OkHttp 5.5.1 is resolved through Ktor 3.6.1. TLS regression tests allow a valid connection and reject a wrong hostname and compromised emSign chain before HTTP data reaches the test server. This establishes the OkHttp path, not the native SDK's separate TLS implementation. The older revision-16 Maven advisory query does not clear the upgraded graph or native dependencies; retain the scoped findings in [maintenance guidance](MAINTENANCE.md).

The [consolidation security review](native-security-review.json) binds the published ARM64 binary and narrows two suspected secret-operation paths. It confirms affected-version markers for five native dependencies, while advisory-specific reachability and full native build provenance remain unresolved. Inspected wallet HMAC derivation does not invoke the cited ctutils comparison methods; inspected Tor SSH features do not establish P256 activation. Neither finding clears other consumers. No supported SDK newer than 6.0.0 was found on 8 November 2026.
